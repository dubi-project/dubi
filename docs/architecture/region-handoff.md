# 区域增长：持久封口与代际激活

当前已落地数据 Group 状态机协议、写入门禁、恢复校验、认证远端交接观察、Root 持久增长授权与任务绑定，以及正式托管后台的**自动严格增长协调器**。已接纳到同一区域的新节点可以自动进入后继代际；这不产生 LocalReady/GeoReady 数据回执，也不实现缩容、成员移除、失盘修复或独立硬件生产资格。

## 为什么不能直接覆盖栅栏

Raft 成员已增加不等于旧参与集合的多数数据确认可以改用新集合。扩容还可能跨越协调器重启、Root leader 变化和快照安装。交接状态因此与数据 Group 自身的 applied index、命令结果一起同步持久化；不依赖进程内记忆，也不按健康删减参与者。

协议顺序是：旧代际封口并取得旧集合严格多数的精确应用观察 → 成员增加与追赶 → 候选栅栏 → 新集合全员持久观察、逐条物理多数复核与 Root 发布 → 精确激活。中间允许读取、复制、成员操作与快照恢复，禁止新的业务 mutation。空 Range 初始化仍走原有受约束控制协议：它没有业务 payload，不能授权该 Range 在封口期间写数据，也不能把临时交接拒绝永久写进它的固定请求 ID。这个短期业务写入暂停是安全交接阶段，不是数据丢失，也不把故障时暂停改为降低多数门槛。

## 已实现的数据原语

- `seal` 绑定完整旧 fence Record 和 Root 的下一代 pending cohort。只允许同 Region、同 Group、紧邻代际和前进的 Root 计划位置；普通增长保留整个旧 cohort，维护移除后的恢复增长则必须保留旧 voter 严格多数、保留当前 Group 成员并加入新身份。恢复增长在旧 Fence 与当前 ConfState 暂时失配时仍然只允许封口，业务写入继续关闭。
- 封口在状态机应用锁内持久生效。后续业务写入在调用模块 Handler、事务或 Pack 写入前被拒绝；拒绝结果也持久保存。恢复后重试同 RequestID 仍返回原结果，需要新意图使用新请求 ID。
- 下一代 `region_fence` 必须对应已封口计划，实际成员位置必须在封口之后；只写候选记录不解除写入封口。第一代及封口前的同代际 epoch 刷新保持原边界；已激活交接不接受任意覆盖。
- `activate` 绑定精确候选 Record 和完整 Root confirmed cohort：成员、代际、计划、epoch、fence 请求与位置必须一致。它是内部协调器断言，不是用户可提交的远端磁盘证明。确定性 Apply 无法读取 Root，正式协调器还必须在提案前认证并重新核验当前 Root 授权。
- 激活后只有当前成员位置/配置仍匹配候选 fence 才允许业务写入。后续成员变化（包括名单恢复原样的 ABA）再次阻止写入，不能复活旧权限。需要受控交接/维护，不自动猜测修复。
- 激活后的下一次封口可以替换交接进度；旧命令成功结果仍保留。重放旧激活只保留第一次结果，不会清除下一次封口。

`RegionFence()` 在同一读锁下返回成员位置、ConfState、最新 fence 与可选交接记录，`RegionHandoff()` 是该本地切点的进度投影；两者都不提供跨节点线性读或 Root 发布权限。现阶段保留最近一次交接及其旧 fence，Root 另保留代际历史；尚无证明归档、Checkpoint pin 或 GC 回收协议。

认证 `Observe` RPC 传递同一切点的交接记录，仍需指定参与者自己的 Root/Group 读屏障和前后 Node/TLS 鉴权。响应必须声明 v5，客户端拒绝旧/缺失格式、错误/超限/孤立交接，以及下一代 fence 缺失交接的响应。它验证封口/激活位置和候选关联，不验证 Root 计划此刻仍授权；协调器必须另行检查。成员 `Active=true` 只代表配置匹配，即使仍 sealed 也可能为真，不可当作写入已激活。第一代确认器明确拒绝任何携带增长交接的观察，不能越过专用增长工作流发布确认。

## Root 增长授权

`AuthorizeRegionGrowth` 接收内部协调器对旧参与者封口的断言，必须精确绑定 Region/Group、下一代 Root 计划位置、旧确认的 epoch/fence 请求与数据位置、新 seal 请求与位置、唯一 ChangeID 和完整期望成员。Root 只允许严格增加节点并保持旧成员角色，不允许借增长缩容、换组或更换旧角色。计划、授权以及任务执行还要求参与者仍在稳定的当前 Root 成员中；不按健康状态缩小集合。

授权记录、带 Region/Generation 的成员任务、active-task 反向索引、命令结果与 Root applied 在同一 Sync 提交中发布。已有确认代际的 Group 禁止直接 Publish 或普通 PlanGroupMembers 绕过授权。Prepare/Change/Transfer 和完成任务沿用原任务检查，同时核对当前 pending 代际与授权；临时 Root 联合配置会暂停授权，不撤销已持久完成的动作。

只有对应增长任务完成、Group epoch 精确前进一次且成员精确匹配，Root 才允许确认新代际；候选 fence 的数据位置必须晚于 seal，不能复用 seal 的请求 ID。Root 的计划/授权/确认位置只互相比对，不与数据 Group 的 index 比大小。Root 完成任务遇到临时拒绝后，用新 Root 切点产生重试请求；任务本身保持幂等。重放相同旧授权可查询历史成功，但不重新建立 active task，也不赋予旧任务执行权。

该记录**不是 Root 自己验证过远端磁盘的密码学证明**。正式协调器先通过认证、定点 Observe 在不缩小旧集合分母的前提下核验严格多数旧参与者已应用同一封口，再提授权；之后仍要核验新参与者候选并完成激活。单独提交内部断言不能作为自动扩容验收。

## 正式自动增长工作流

托管 Server 在建组、初始确认之后调用增长协调器。只有当前 Root leader 推进；每轮选择一个区域，增长及物理补齐受 2 分钟上下文约束，单次旧参与者观察至多 3 秒。轮转游标和探测起点只影响调度，不是权限或持久进度；关闭时取消并等待工作者退出。

1. Root 读屏障后读取 `RegionProgress` 单切点：当前/待定代际、Group、当前/待定增长授权、成员任务和资格。与当前 Root 区域成员比较，只规划严格超集，不按可达性缩容。
2. 核验旧 fence 确实对应当前 Root 确认，已有上一代增长必须先激活。提交绑定下一代完整计划的 seal。
3. 对旧集合按固定分母取得**严格多数**相同 seal、旧 fence、实际成员位置及 Root/数据读屏障；不可达或尚未追上的节点不计数，授权前复验 Root。旧角色保持不变，新增节点经 learner 追赶后晋升 voter，无用户票数参数。
4. 现有成员任务执行器准备节点、增加、追赶和晋升；增长协调器在任务 pending 时等待，不越过它发布候选。新节点不重新 bootstrap。
5. 任务完成后核验封口之后的精确实际配置，提交候选 fence；先按授权封口从旧来源给新增节点补齐当前权威引用，再逐一观察**全部新集合参与者**的相同候选和交接记录。随后新节点重新获取完整且经认证的封口引用清单，对每条记录验证自己本地 Pack，并直接向候选集合中的其他 Node 取得认证持有观察；每条均须达到固定新集合的严格多数，错误身份、重复 Store、滞后 Root 观察和缺字节不能充数。复验 Root 后才确认新代际。补齐与逐条复核本身没有发布权限，可以在一名旧成员离线时先做并反复重试。
6. Root 已确认但数据尚封口时，提交绑定完整确认记录的 activation。可从任一可用参与者探测/路由提案，不固定依赖最小 NodeID。其他成员通过正常 Raft 应用激活；未应用的本地状态继续拒绝写入。新一轮封口必须在这一激活之后。

跨阶段重启、Root 换主或丢失响应都重新读取持久状态，不凭内存猜测。相同 seal/candidate/activation 使用确定性请求 ID；Root 计划、授权、确认的临时持久拒绝则在新 Root 切点重试，由不可变计划/任务保持成功幂等。观察后资格/计划/任务改变会拒绝该轮发布；每次真正 Apply 仍执行自身的状态约束，不宣称跨 Group 原子授权。维护移除后的恢复代际沿用同一增长协调器，并继续复用普通 Placement/Repair 流程。

旧集合不足严格多数确认 seal，或任一新集合参与者不能确认候选时，交接保持 pending，不自动取消、移除它或降低多数分母。其他区域轮转推进。旧多数封口只让成员任务和新节点预热向前推进：**当前候选发布仍要求新集合全员可观察**，因此永久离线的旧节点仍会阻止最终确认；这不是成员移除或新节点再平衡完成。Root 确认后的 activation 不需要重新获得每台节点的在线确认。

逐条物理复核是当前发布前的一次新鲜检查，不是持久持有租约：结果不作为可复用回执保存，节点之后失盘仍须由读写路径重新检查。当前每轮增长/复核受 2 分钟总时限约束，超时从持久封口和已补齐的 Pack 重试。封口清单现有经过整件校验、与 seal/工件/引用集摘要绑定的有界分页遍历；**游标只标记清单位置，不证明前页的 Pack 仍存在**，所以正式发布仍执行完整物理复核，大清单仍缺安全可恢复的覆盖进度。要跨重启复用物理观察，须先定义持有留存、失卷失效与末次复验的协议；不能只持久化游标后跳过前页。跨 Root/Owner 的在役身份隔离、受控移除旧成员和新节点加入后的自动再平衡仍未实现。

Pack 读取失败（包括卷标记/目录身份变化、失卷和关闭）不会产生持有回执；已知 Pack 完整性损坏单独报告为数据损坏，其他无法完成物理读取的错误归为该 Node 暂时无法证明持有。候选逐条多数计算仍以完整成员名单为分母，只计实际验证成功的不同 Store；坏卷节点不能充数，也不会因错误字符串差异阻断其他节点形成真实多数。卷恢复后重新读 Pack 才能再次计入，不复用旧观察。

记录索引也遵守同一门禁：Pebble 明确报告的损坏或索引值损坏属于数据损坏，其他索引读取错误属于该 Node 无法证明持有；二者均不得解释成“记录不存在”，也不产生回执。当前仍无跨重启的持有留存或失卷失效代际，因此分页游标只允许遍历/预热，不能累积成可跳过前页的发布证明。

## 版本、快照和故障边界

Engine 状态及两类快照使用 **v5**。v4 不认识封口/激活和写入门禁，不能混用；旧非空状态明确拒绝打开，不自动迁移或重写。Root 仍使用现有 v1 信封，但新增增长记录与命令，不代表旧二进制支持它们或允许混合升级；缺失授权的旧人工增长历史不能通过当前快照语义校验，不自动补证据或迁移。Pack 容器与本地 Pack 引用格式不变，各 Tenant/Engine 继续混写 Pack。

快照带交接状态及相关命令结果。固定切点校验旧 fence、封口位置、候选关系、激活断言和结果摘要；错误镜像在清空目标或写 Pack 前拒绝。文件捕获后的 live Apply 不改变已捕获状态。Sync 结果不确定时状态整体停止服务，重开后以实际持久结果为准。

已有单元/持久状态测试覆盖封口和激活重启、旧激活重放、成员 ABA、封口阻止模块调用、新建空 Range 仍不能写数据、两类快照各阶段往返与语义损坏、两种 Sync 不确定结局、旧格式拒绝及命令互斥。它们不替代真实多节点自动扩容、每笔数据多数回执、WAN/物理掉电和生产发布验收。

Root 两类快照在同一固定视图中验证增长记录、前后代际、任务、Group 与原始授权结果的交叉引用；待执行、成员已完成、代际已确认和后续历史阶段均可恢复。缺失记录/结果、错误摘要、旧角色改变、删掉任务的增长标记或候选早于封口都拒绝恢复，不能先清空目标再报错。单元及持久状态测试覆盖原子 Sync 的两种不确定结局、重启、历史重放、临时拒绝恢复与快照损坏；这些仍非真实自动扩容验收。

协调器测试覆盖各阶段丢响应、重新创建协调器、Root 联合配置临时拒绝、观察后失去资格/领导权、缺失或不一致参与者、区域公平性、跨代际激活顺序及关闭等待。真实 CLI/TCP/mTLS 测试由正式后台自动执行 3→4→5，包含封口途中整组重启、完成后停两节点和全群冷启动；测试不手工提交增长命令。本机目录不是独立故障域，成员/栅栏恢复不是每笔业务数据耐久回执。下一步仍需 per-write 代际/持有证明、小区域跨区确认、Placement/Repair、真实磁盘/WAN 与长期资格。
