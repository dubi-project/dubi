# 内存与首次 Range 延迟验证（2026-11-05）

本轮在 Range 迁移六小时长测结束后进行。实际运行与测试均在 VPS；开发机仅阅读、静态检查与交叉编译。九节点原长测结论见[Range 迁移验收](range-migration-soak.md)。

## 内存判断与修正

六小时长测结束约五小时后，九节点仍是原进程，无重启；RSS 约 117–144 MiB，与长测尾部相近，没有观察到空闲期间继续线性增长。TT02 加入 Go 指标后的短样本，最近 GC 的存活堆约 17–19 MiB；GC 持续发生。重启后第二组短样本约 12–14 MiB。重启、缓存预热和 GC 时点不同，不能将两组堆差异归功于延迟优化，也不能据此宣称排除了所有泄漏。

代码审查发现默认预算边界问题：cgroup v2 的 `max` 原先会提前返回，跳过物理内存回退；v1 的不限额数值可能被当作真实大预算；固定 512 MiB 下限对小容器没有留出空间。现在取可用 cgroup/物理内存较小值的约 50%，不设置固定下限，保留显式 `GOMEMLIMIT`。本批 VPS 原来已走物理内存回退，因此这些问题不是本次 RSS 上升的已证实原因。

现有 `/metrics` 新增十项 Go 指标，以区分存活对象、保留页、释放页、累计分配与 GC；不新增端口，不强制 GC，不公开堆内容。Go 软预算不等于进程 RSS 限制。

## 首次写入优化

原路径创建和激活 Range 约需 0.7 秒，随后等待后台发布初始 placement 又花 2.85–6.65 秒。改为首次写入通过现有 `SetRangePlacement` Root 命令帮助完成初始化。Root 继续验证 Active Range、Owner、Epoch 和确认的 Region cohort；写入必须看见匹配的持久 placement，不能仅凭提交成功继续。

该入口不刷新、扩张已有 placement，不更改多数派、成员或格式。区域尚未形成时仍由后台推进，等待服从请求取消及原 30 秒上限。正常已有 Range 的本地准备检查不增加共识往返。

同一 TT02 入口、每组四个新 Tenant/Range，各 16 次写入、48 次三区域读取，所有顺序请求成功：

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 首次写入 4 样本（毫秒） | 8188 / 4129 / 4334 / 4478 | 1782 / 1765 / 1713 / 1761 |
| 首次写入中位数 | 4406 ms | 1763 ms |
| 首次写入最大值 | 8188 ms | 1782 ms |
| 已有 Range 写入中位数（12 次） | 572.5 ms | 583 ms |
| 三区域入口读取中位数（48 次） | 1606.5 ms | 1616.5 ms |

首次写入中位数减少约 60%。这是低速小样本对照，不是吞吐或尾延迟资格；普通读写没有显著改善。新路径首次 placement 阶段至多 392 ms。

## 普通读与并发限制

TT02 服务端读取约 0.58 秒，三段主要等待分别为请求成员准入、初始物理多数检查、最终当前性复核，各约 0.19 秒。Owner 引用读取数毫秒，本地 Pack 读取接近零。CLI 跨区域完整耗时还包含网络与转发，不应与这些父子计时重复相加。

本轮没有删除或缓存跨请求的物理多数证明。下一项性能工作应针对同一请求内的屏障复用，并覆盖覆盖写、Fence/代际变化、Root 不可用和持有丢失的拒绝行为。

六个相同请求并发初始化一个新 Range：四个成功，RangeID、Owner 和 applied_index 相同；两个返回 `ResourceExhausted: Root join is busy`。当时 Root admission/discovery 服务只有四个共用处理槽。后续调用链核对确认，限流发生在 CLI 读写之前的 DiscoverRoot；服务端非 voter 的普通 Root 读屏障使用 Group ReadIndex，并不经过该入口。保留这两次失败，不能宣称六并发零失败。应单独处理节点发现与成员管理的准入隔离，不能简单放开无限并发。

关闭临时 Trace 后重启 TT02，两条原失败请求使用相同 RequestID 重试成功，仍返回原 applied_index，未新增逻辑写入。四个新 Range 及并发测试记录均从三个区域入口读取校验，15 次全部成功。节点、元数据实例和卷身份保持不变。重启检查脚本起初误将动态可用容量纳入卷身份比较，导致断言失败；已保留原记录，改为仅比较 VolumeID、路径、状态和设备，不重复重启。
