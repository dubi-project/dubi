# 租户配额：三地域 VPS 验收（2026-11-06）

本文前半部分保留同步严格配额的历史结果。用户随后确认改为允许并发短暂超额的软配额；新方案见 [租户配额](../architecture/tenant-quota.md)，复测结果见本文末尾。以下严格“不超发”断言不再代表当前产品要求。

## 环境与方法

- 新加坡、法兰克福、多伦多，每个 Region 三台 VPS，共九个真实节点。
- 九节点统一运行二进制 SHA-256 `9d2c51d9485cdc340de77c15f7ef288654ce1fdfccdf023f94489ca2dc0a380d`。逐台升级，保留 Node/Store 身份、原有数据和旧二进制备份。测试时 Root leader 位于 FF01。
- 请求入口为 SG01、SG02、FF01、FF02、TT01、TT02，覆盖每个区域的 Root voter 和普通节点。每个入口访问三个区域首次写入建立的 State Range。
- 客户端直接运行在 VPS，通过本机 HTTPS 业务入口调用 Config/State；使用集群 CA 和服务器名称验证证书，不包含开发机到 VPS 的请求往返。Runtime 决定后续跨节点路由。
- 比较同一版本的未计量对照、计量但不限额、计量且限额为 16 MiB 三种状态。对照组是升级前建立的空测试租户，升级完成后才写入测试数据，不涉及历史数据迁移，也不是公开的“关闭计量”配置。对照组仍保留当前代码中判断是否计量的 Root 查询，因此测得的是启用完整计量后的额外成本。
- 每次写入 1 KiB 值，使用新键和新 RequestID，紧接着读取并校验完整值。每种状态有 18 个入口/Owner 组合，每个组合预热两组 PUT/GET，然后记录八组 PUT/GET。最多三个并发客户端，每个客户端顺序请求；使用持续连接。
- 合计 1,080 次请求：864 个正式计时样本，216 个预热样本。全部成功且读回一致。失败不会通过自动重试从结果中消失。首次建立 Range 的约 3–7 秒耗时不计入稳定运行样本。

这是正常拓扑下的小请求、低并发短测，不是吞吐容量、故障切换或长时间运行验收。下表的“跨区”指入口与初始 Owner 所属 Region 不同，不表示每一段数据传输都必须跨区。

## 结果

延迟单位为秒；表格单元格为 P50 / P95，P95 使用样本的最近秩分位数。

| 操作 | 未计量对照 | 计量、不限额 | 计量、16 MiB 限额 |
| --- | ---: | ---: | ---: |
| 区域内写入 | 2.360 / 3.077 | 3.816 / 4.772 | 3.726 / 4.806 |
| 区域内读取 | 2.038 / 2.379 | 2.040 / 2.456 | 1.982 / 2.376 |
| 跨区域写入 | 2.160 / 2.741 | 3.607 / 4.668 | 3.551 / 4.571 |
| 跨区域读取 | 1.918 / 2.482 | 1.976 / 2.550 | 1.950 / 2.488 |

每种状态的区域内每类操作为 48 个正式样本，跨区每类操作为 96 个正式样本。有限额组的区域内写入中位数增加约 58%，跨区写入增加约 64%。不限额计量也承担同类开销，设为不限额不能绕过同步计量。

按区域分别统计区域内写入中位数，每个单元格包含两个入口各八个样本：

| 区域 | 未计量对照 | 计量、不限额 | 计量、16 MiB 限额 |
| --- | ---: | ---: | ---: |
| 新加坡 | 3.009 | 4.713 | 4.714 |
| 法兰克福 | 1.567 | 2.374 | 2.440 |
| 多伦多 | 2.360 | 3.816 | 3.726 |

各区域、入口和 Owner 的分布不同，不能把汇总表中“跨区”与“区域内”的数值直接解释为网络距离的影响。配额对照保持了相同入口与 Owner 组合。

网络取样：区域内平均约 0.3 ms；SG—FF 约 153 ms，FF—TT 约 95 ms，SG—TT 约 230 ms，每个方向取三次 Ping。计量轮资源抽样中，三个入口所在机器的 CPU 仍有约 80%–90% 空闲，服务内存约 70–100 MB，没有观察到资源打满。该抽样不代替持续资源监测。

## 配额正确性

- 两轮计量性能测试的 360 次写入，加上各租户的初始种子数据，与账本逐字节核对一致。三个租户各使用 127,892 字节，预留均为 0；从其他区域查询仍一致。
- 单独创建 4 KiB 限额租户，六个入口同时写入六个不同的 1 KiB 值。三笔成功，三笔返回 `409 quota_exceeded`；三个区域查询的用量一致，没有超发。
- 删除突发测试数据后，继续验证增长超额拒绝、缩小已有值后允许再次增长，以及跨区域删除。最终三个区域均查询到 used=0、reserved=0。
- 性能样本与并发超额测试分开运行，避免把预期拒绝当成成功写入延迟，也避免突发检查干扰性能采样。

## 判断与下一步

代码中每笔计量写入都同步执行 Root 额度预留、准入检查和结果结算。相比同版本未计量对照，正常路径新增两次 Root 命令，以及待处理检查、准入和命令结果确认等多次 Root 读屏障。跨洲往返会串行叠加，实测新增写入等待与这条路径一致。

同时，Config 未计量对照本身也已是秒级。它在鉴权、路由、State 元数据及数据读取中存在多次同步确认，不能把原有底座 Record 写入的延迟当成这条业务路径的延迟。当前结果没有逐阶段追踪，不把全部基线耗时归到某一个调用。

该轮之后，按用户确认取消每笔写入的全局额度预留和结算，采用本地缓存准入、后台用量批量汇总。新的验收要求是允许短暂超额、最终计量准确、同步后阻止继续增长，并保留租户授权、幂等和持久数据安全。

## 软配额第一轮复测

- 九节点统一升级到 `5883a9bd397b0cbce9b40fb1c300ac6368705877ad9ed08c7d6208be2f7cb39d`；Root Leader 变为 SG02。因此不能把绝对耗时与前述 FF01 Leader 的旧版本直接比较。
- 仍使用六个入口、三个 Owner Region、1 KiB 值。每个组合预热两组，再记录四组 PUT/GET；三种模式共 648 次读写，全部成功且读回一致。
- 开启计量的 216 次写入和种子数据逐字节核对，三个租户各为 77,180 字节、reserved=0。异步汇总与业务数据一致。
- 本区域 PUT 中位数：未计量 3.872 秒，计量不限额 4.496 秒，16 MiB 软限额 3.945 秒。有限额相对基线增加约 1.9%。对应 GET 为 3.789、4.315、3.773 秒。
- 不限额轮同时出现 Geo 数据同步积压、传输繁忙与超时日志，读取也变慢。不能只把阶段差异解释为配额成本，更不能宣称异步后开销恒为零。此次采样不是性能容量承诺。
- 后续收紧了缓存临界区：元数据读取移到准入锁外，热路径只检查内存；低流量时合并 5 秒的更新，满批立即排空后续页，减少后台 Root 小请求。节点尚未看到租户目录时不推进计量游标，避免跳过待汇总数据。

证据目录为 `/tmp/dubi-soft-quota-wan-20261106`，第一轮样本为 `samples.json`，计量核对为 `usage-verification.json`。请求在 VPS 上执行，不在开发机跑业务压力或集成测试。

## Runtime 统一入口调整（2026-11-06）

配额服务改由 Node Runtime 统一持有，State 不再装配或调用配额服务。所有 Engine 的逻辑写入统一进入 `Bound.Mutate`；Engine 只提供逻辑键、新大小和普通业务结果适配器。Runtime 使用现有读取中的引用元数据取得旧大小，统一处理准入、重放、成功、持久拒绝和未知结果。Handler 使用 `Transaction.PublishRecord` 原子发布引用及逻辑大小。后台维护不再依赖 HTTP Gateway 是否启用。

本次不改变软限额和用量持久格式，也不增加配额专用网络查询。已开启计量的租户不能通过旧原始写入入口绕过逻辑计量。
