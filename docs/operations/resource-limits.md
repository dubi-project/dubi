# 基座资源界限

这些是内部默认保护，不要求用户逐节点配置。它们限制参与预算的工作，不是对整个进程 RSS、所有 IO 或 gRPC 接入连接数的承诺。完整 P02 仍未完成。

数据入口现在还有一个统一的请求字节预算，默认 128 MiB，覆盖 Record 读写及 Dataset 等 Node-authenticated 数据请求，从准入开始持有到响应完成。预算满立即返回 `ResourceExhausted`，不会排队，也不会降低数据多数门槛。`dubi status` 的 `local_repair.request_budget` 展示当前、峰值和拒绝次数；这是进程内背压指标，不是对外租户限流或全进程 RSS 上限。

Volume 迁移和 Pack 重写共用节点维护门禁：同一节点同时只运行一个 Volume/Pack 维护操作，维护工作最多预约 128 MiB 的保留字节。预算耗尽会让后台稍后续跑或让显式维护命令返回忙碌，不会降低前台数据写入的多数要求。`status` 会报告维护预算的当前/峰值占用和拒绝次数。

## 后台维护调度

本地权威引用修复每页最多 64 条元数据，载荷仍逐条校验/拉取，不会同时缓存 64 份正文；每页维持两分钟期限与共享 IO 预算，游标只在该页完成检查后推进。该批次用于摊薄 WAN 上的 Root/Owner 屏障，并不等于下述 Geo 待办每轮八项的调度批次。

本地 Repair、Geo 修复、卷迁移/容量均衡、Pack 压缩和备份捕获现在共用节点级维护调度。默认同时准入一个本机维护任务；前台活跃时优先让出，持续繁忙超过 30 秒仍允许后台以较低速度推进，避免永久饿死。数据 Store 的普通读写以及数据 RPC 都登记前台活动；Raft 控制面不使用这个维护槽。

参与调度的 IO 共用默认 8 MiB/s、一个速率窗口的突发额度；前台活跃时降为四分之一。等待按 FIFO 串行预约，不在 Store/Pack 锁内睡眠。Record 读写和修复按载荷量预约；卷迁移后台每次最多搬一条记录、扫描至多 64 条索引；重写压缩分批读取索引、逐条校验和同步位置，并在记录之间让出 Store 锁。备份按最多 256 KiB 的读取块参与限速，捕获完成后释放维护任务槽，上传期间继续共用速率额度。认证远端 Repair 共用目标节点的 IO 额度，不在跨节点调用中等待第二个独占任务槽。

`dubi status` 的 `local_repair.maintenance_io` 显示任务、前台活动数、默认速率、累计预约字节及延后次数。这个计数包含保守预约，不等于磁盘实测吞吐；内核、Pebble Compaction、Raft 和普通远端物理持有观察仍有各自的 IO。它不保证整体 RSS 或整机磁盘/网络的硬速率。

## 文件系统空间预算

同一进程按实际文件系统设备共享在途空间预约，覆盖 Pack/Volume、记录索引写入准入、Raft 日志及普通 Pebble 的 WAL/SST/Manifest 写入、快照文件和恢复暂存 DB。多个目录、Registry 或组件不能各自重复使用同一块盘的剩余空间；数据 Volume 有空间也不能绕过元数据所在文件系统的准入。记录 Put 在 Pack append 前为索引预留 64 KiB。

可选数据及恢复暂存写入保留至少 1 GiB 或总容量 5% 的较大值；已提交的 Raft/LSM 持久化可以使用这部分保护空间，仍须避开其它在途预约。Pebble 按每次实际 Write/WriteAt/Preallocate 预约，快照按最多 256 KiB 写块预约，写入完成后释放；不按整个快照大小长期扣住预算。磁盘压力检查同时考虑同设备在途预约，实际 available 字节仍保持原始观测。

这是进程内保守准入，不是文件系统配额、实际预分配或对外部进程写盘的控制；空间观测、内核延迟分配及真实 IO 仍可能失败。预算不能取消已提交的 Raft 命令，真实持久化错误仍按既有失败关闭机制处理。

## Geo 待办队列

记录修复和元数据镜像均按持久游标轮转，每轮最多读取 8 项；在尝试前同步记录游标，失败或重启后从后续任务继续，绕到末尾才回到队首。记录任务使用独立有限期限；镜像支持批量传输时，八项共享一次最多 3 秒的重试轮，各自取得新鲜计划后按目标组批，旧传输仍每项最多 3 秒。发现扫描单独限制为 20 秒且轮转起始 Group，不吞掉整个重试窗口；容量探测最多 6 个并行请求，每个至多 3 秒，失联区域不能按节点数串行耗尽修复期限。游标只表示尝试顺序，不能删除欠账：仍需真实多数复验、目标持久 Result 或已确认的引用覆盖切点。

正常重试和状态查询不再整批解码待办，也不因达到旧的 4096 项批次上限而停止登记。启动按持久键重建计数，Save/Delete 同步成功后才更新内存计数；不确定写入使句柄拒绝继续服务，重开后恢复。账本仍受磁盘容量及现有写入背压约束。

## 连接与握手准入

正式 Node 内网 RPC 监听最多保留 128 个已接受连接，包含尚未完成握手的连接；超额连接关闭后继续 Accept，不停止服务。TLS 最多并行 8 次握手，10 秒握手/HTTP2 建连期限；复制的凭据共享同一握手额度。每条 HTTP2 连接最多 64 个并行流，Header List 最多 32 KiB。槽在实际 socket Close 后归还，重复 Close 不重复释放。可选公开 HTTPS 监听另有 32 个连接上限。

这些是当前默认的小集群保护，未取得大规模节点数量下的连接容量资格；它们不代替已有的 RPC 消息、并发、证书有效期和成员授权检查，也不限制内核监听队列或出站连接总数。

不可变记录组件已由正式 Runtime 持有，限制 Key 4 KiB、载荷 64 MiB、登记文件 4 KiB、索引项 16 KiB；每个 Store 串行执行 Pack/索引操作，在进入锁后才复制载荷，避免等待调用各保留一份 staging。摘要及身份先检查固定长度再解码。父级沿用至多 1 MiB 的 Store 清单读取边界，当前必需资源只有记录索引。该限制不包含调用者自身缓冲、Pebble/Pack 编码、返回载荷或全局 RPC 解码内存，也不是公平调度/全局 IO 预算。后续数据入口仍须统一准入；见[不可变记录](../architecture/immutable-records.md)。

## 能力事务结果与持久行

Handler 产生的持久 Result 以完整 JSON 行计最多 64 MiB，与文件快照单行及权威引用的发布关联上限一致；不是允许 64 MiB 二进制返回值。底座先检查原始长度，再根据实际头部编码、Base64 长度和可选字段计算完整大小，通过后才编码结果和执行事务 Pack 写入，避免先落盘才发现结果无法恢复。Handler 拒绝文本原始长度最多 64 KiB，编码时仍计入 JSON 转义。

超限会丢弃本次全部 KV/引用修改，持久保存固定拒绝 Result 并推进 applied，不使已经提交的 Raft 日志停在同一命令。相同 RequestID 重放保留原拒绝；后续正常命令可继续。真实存储/Sync 错误仍保持失败关闭，不能被当作应用拒绝吞掉。

普通 enginestate 持久点查先检查 Pebble 借用行不超过 64 MiB，再复制内容；权威引用行进一步限定 16 KiB，其 Range/Keyspace 关联限定 64 KiB，Result 关联仍为 64 MiB。损坏/旧超限行返回错误，不伪装为空值、不重写或截断。Pebble 自身读取、Handler 构造原始载荷、JSON 编码缓冲、普通 KV 的累计暂存及 RPC 接收/响应并发不包含在这些上限中；它不是全进程内存预算或完整 P02 完成声明。

## 封口引用清单

每个 enginestate 最多一个固定引用准备对象，包含 ReadIndex 等待；内部读屏障期限 10 秒，构建遵从调用方上下文，数据库关闭等待准备对象 Close。清单沿用既有快照集合和至多 1 TiB 流式文件上限，不将全部引用装入内存。单引用仍限制 16 KiB，Range/Keyspace 关联 64 KiB，Result 关联 64 MiB；关联值只在单次验证中借用，不额外克隆整行，也不写入清单。Pebble 读放大和 Result JSON 解码仍可能分配内存。

通用流解码新增可收紧的逐项边界，不能超过原有 64 KiB key / 64 MiB value 上限，先检查声明长度再分配和读取正文。清单采用至多 1 MiB + 4 KiB 的单行界限以容纳 seal 头；引用行另做 16 KiB 语义检查。末尾 SHA-256/EOF 未通过前，遍历回调不是完成证明。尚无全节点清单磁盘预约、缓存淘汰、跨 Group 公平调度或任务保留预算，当前原语未由后台自动反复创建；不能把单视图限制当成完整 P02/P07。

## Raft 发送

Raft 自身为每个 Group 的每个 Peer 设置 8 MiB 在途 Append 字节窗口，同时保留 256 条消息上限；这发生在 Transport 准入之前，避免在 Group 锁内一次生成数百 MiB 的历史日志批次。字节窗口是 Raft 库的软上限，允许最后一条消息越过边界，单个超大日志项也不能拆开；不能把它理解成整个进程的 RSS 硬上限。它不改变成员集合、多数派或确认规则。持久日志的 `Entries` 使用单个有界顺序迭代器，按原字节限制返回连续记录，缺失或损坏仍报错，第一条超限记录仍按 Raft 接口约定返回。

每个 Transport（正常运行时每 Node 一个）按通道维护跨所有 Peer/Group 的字节预算：

| 通道 | 字节上限 | 每 Peer 等待队列 | 用途 |
| --- | --- | --- | --- |
| 控制 | 8 MiB | 64 条 | 不含 Entries 的非快照消息，以及用 Entries 携带 token 的 ReadIndex/ReadIndexResp |
| 日志 | 64 MiB | 256 条 | 携带 Entries 的复制/提案消息 |
| 快照 | 128 MiB | 1 条 | 旧内联 MsgSnap 上限 64 MiB；文件流组件额外预约有界帧缓冲 |

通过 protobuf Size 先校验、预约，再分配序列化副本。字节从进入队列到 RPC 完成一直占用，不能通过增加 Peer 或让队列出队绕过。队列/预算满立即返回错误，由 Raft 的发送失败与快照报告流程重试，不在 Raft Ready 路径等待空闲预算。无地址、编码失败、队列满、异步发送失败、关闭取消都会释放预约；关闭等待 worker 结束后释放未处理队列。

每 Peer 的控制、日志和快照各有 worker，控制与日志共享并发安全的 gRPC 连接，快照独立流。慢日志 RPC 不会在应用队列中阻挡心跳或 ReadIndex；这不保证饱和网络、CPU 或内核调度下的控制消息延迟。消息可能跨通道重排，遵循 Raft 允许网络重排的模型。Raft 不自动重发丢失的 ReadIndex 请求/回复；启动恢复以有限单次期限重试，并在取消时退出，普通读请求仍由调用方期限控制。

`Transport.ResourceStatus()` 暴露各通道当前/峰值占用和拒绝计数，供后续统一诊断接入。它不包括调用者原始 protobuf、gRPC 内部缓冲、连接开销、Raft 内存日志以及状态机解码后的对象。

## Host 的 Group 隔离

后台时钟不再串行等待全部 Group：每 Group 至多一个活动 Tick worker，繁忙时跳过当次 Tick，不为同一 Group 累积工作或恢复后突发补发 Tick。慢 Group 的恢复/落盘可以阻塞其自身，但不在共享时钟上拖住 Root 和其他 Group。显式 `TickAll` 仍保留同步语义，供确定性调用/测试使用；该改动不是磁盘 IO 调度或心跳时延保证。

`AddGroup` 在 Host 锁外打开日志和恢复状态，用 opening 标记拒绝同 ID 并发打开，恢复期间其他 Group 仍可被路由。关闭阻止新打开和新 Tick，等待已开始的工作、关闭 Group 后才释放 Store 锁；并发 Close 等待同一关闭结果。慢 IO 本身仍可能延长关闭时间，不能强制中断任意文件系统调用。

Raft 追赶快照由 Host 每 5 秒按需检查：leader 的当前参与者落后至少 10,000 条已应用日志，且距上个快照也至少 10,000 条时，才使用现有流式准备接口。每 Node 最多一个活动构建，Group 轮转，锁繁忙时跳过而不排队；无明显落后成员或已有快照正在传输时不反复生成。磁盘准入、准备对象、取消和完整持久发布边界保持原值。压缩镜像不含已提交的新成员、其确认位置还在镜像之前时，允许绕过普通日志条数和旧传输在途条件，生成包含该成员的新一致镜像；这不放宽接收端验证。已有镜像覆盖但尚未推进到镜像位置的同一成员不会因持续写入反复触发构建；实际推进或新身份才允许刷新。该机制不增加后台传输并发，不负责旧 artifact GC，也不是累计镜像磁盘配额。

## 快照接收

Server 在验证 Header、来源和大小后，分配接收缓冲前，执行非等待准入：最多同时 2 个快照、编码缓冲总计 128 MiB。预约持有到接收、SHA-256 验证、解码、状态机持久安装和 ACK 返回结束；取消、损坏、超限和安装失败也释放。资源不足返回 ResourceExhausted；不占用这些槽的普通 Step 可继续处理。

新增文件流按最多 2 MiB 的编码帧空间预约，旧内联镜像在格式判定后补足整份编码预约再分配；均占用相同的接收槽直到持久安装/ACK。文件发送还要求全 Transport 最多 2 个排队/活动流，防止小引用绕过文件句柄/活动流限制，队列拒绝或关闭时同步归还。正式 Node 的 Root 与 Engine Group 均已使用文件路径；目录关联采用固定视图点查，临时恢复 DB 共用有界批次组件，但不代表统一 RSS/IO 预算。详见 P03 的分层验收记录。

快照接收前后、EOF 和 ACK 重新检查现有 TLS 会话授权，防止传输跨越证书/CA 有效期后仍被接受。权限失败释放接收槽和字节预约；文件导入保持 PermissionDenied，不误报为可重试的网络故障。若安装已持久化才在 ACK 时失效，仍保留已安装状态；这不是主动连接吊销。

接收端另有最多 8 个首帧等待槽，10 秒未收到首帧即返回 DeadlineExceeded。验证通过后，每次等待数据帧或 EOF 最多 2 分钟；整条接收/安装上下文按声明大小设有限总期限，最多 24 小时，持续小包不能延长它。空闲计时只覆盖等待网络，不覆盖消费上一帧的本地 IO；总上下文仍不能强制中断文件系统或已交给 Raft 的持久恢复。

gRPC 的 Recv 不直接响应派生上下文，接收由独立有界 worker 等待；超时先退出 handler，让 gRPC 关闭该 stream 并解除阻塞。全 Server 最多 10 个阻塞 Recv worker，worker 自身直到真正退出 Recv 才释放资格，不能用连续超时累积线程。过载不排队，返回 ResourceExhausted；普通 Step 不占这些槽。

当前解码单值、恢复临时 DB 和 gRPC 可能产生额外内存，编码预算不是全进程 RSS 保证。每连接并发、总连接数、整个 RPC/状态机内存、后台 IO 调度及根据部署资源自动确定预算仍需继续治理；首帧并发限制不是 TLS 握手/连接级准入。持久资源清理/GC 保护和真实主机/磁盘/WAN 大状态资格未完成。

正式发送端使用分阶段有限期限：传输无进展 2 分钟、安装基础 15 分钟并按大小增加至最多 6 小时、总期限按大小计算且最多 24 小时。接收端独立执行上述首帧/空闲/总期限，不信任客户端一定使用正式发送器。超时归还网络侧预约，不代表已经持久化的恢复被撤销，也不能强制中断阻塞的本地文件系统调用。公式与验证边界见 [流式快照](../architecture/streaming-snapshot.md)。

## TLS 连接生命周期

正式内部 Server 约每 6 小时平滑更新连接（±10% 抖动），旧流最多 25 小时宽限；对端证书链失效则提前直接关闭 socket。双方 transport 对每次 IO 和空闲连接检查当前有效期，每连接一个定时器，最长每分钟复核墙上时钟。该保护覆盖连接存活期限，不限制总连接数、握手并发或全局解码内存；角色和成员检查仍在 RPC 层。详细验证及时间边界见[节点加入与续期](../architecture/node-enrollment.md)。

## 验证

不可变记录持有观察 RPC 为每节点两个活动请求、10 秒内部上下文、20 KiB 请求/响应（描述 16 KiB）；同一个正式 Store 串行读取实际 Pack。准入在 protobuf 解码后，不包含 gRPC 初始接收分配；读取载荷最多 64 MiB，验证后不把载荷发回网络。取消不释放仍在执行不可中断 IO 的槽，处理结束才归还；过载立即拒绝，不创建无限后台工作者。接口只提供物理观察，没有数据复制或多数耐久承诺。详见[不可变记录](../architecture/immutable-records.md)。

独立的不可变记录发送 RPC 每节点最多两个处理槽和两个实际 Recv worker，接收 body 分配前非等待预约，总计 128 MiB；单条最多 64 MiB，数据帧最多 1 MiB，头/响应最多 20 KiB。首帧 10 秒、后续帧和 EOF 空闲 15 秒、总上下文 5 分钟；超时返回 handler 后由 gRPC 取消底层 Recv，worker 实际退出前继续占槽。接收完整且校验成功后同步落盘，不可中断 IO 完成前不释放 handler/body 预约；发送端每 GroupClient 两条活动请求。预约不含 gRPC 解码、Store 克隆、Pack 编码/读验和调用者载荷，不能宣称全局 RSS/连接/磁盘 IO 预算或硬性五分钟终止。没有新增部署配置，也不是 Placement/自动补齐或多数确认。

不可变记录 Get 与 Put 共用上述服务端两个处理槽及 128 MiB body 预算；读取前预约，保留到发送完成，另有最多两个实际 Send worker。超时 worker 持有的仅是独立有界帧，不是整个大 body；gRPC 取消后待 Send 实际退出才释放 worker。Fetch 客户端与 Put 共用两个活动请求，独立的接收 body 预约上限 128 MiB，并保持到本地 Store.Put 真正返回；最多两个实际 Recv worker。头最多 20 KiB、数据帧最多 1 MiB，客户端单帧解码上限为 1 MiB + 20 KiB。首帧 10 秒、帧/最终状态空闲 15 秒、总上下文 5 分钟；完整字节但最终错误/超时不发布本地索引。源/目标不可中断磁盘 IO 期间不释放相应额度；不把此预算称为 gRPC 统计保留或全进程 RSS 上限。

封口清单回补的小记录读取批次最多 32 条、总载荷 4 MiB，请求描述总上限为 32 × 16 KiB + 4 KiB。它与普通 Get/Put 共享原两个处理槽和 128 MiB 字节预约，不扩大协议处理槽或原传输总并发上限；数据帧和空闲期限沿用上述限制。每批执行传输前、IO 后、最终状态三次新鲜 Root 授权；逐条验证来源身份、描述、长度和摘要，整个批次最终成功后才开始逐条本地持久写入。批次不提供跨记录原子落盘：本地 IO 失败可留下已验证缓存，后续按实际字节断点续跑，不生成逻辑引用或耐久票数。大于 4 MiB 的单条记录仍用普通 Get；旧服务端仅在未返回任何批次帧即报告 Unimplemented 时允许回退，权限错误和部分流不允许此回退。

新节点的封口清单物理回补最多两个小页流水处理，重叠网络等待和本地落盘；小页在途载荷合计最多 8 MiB，生产者另保留一个有界的描述页，不保留第三页载荷。该界限不含 gRPC 解码、Store 克隆和 Pack 编码，不是进程 RSS 硬上限。超过 4 MiB 的记录先等小页全部结束，再走原单条路径；后续小页也等该大条处理结束才开始。每页继续使用原来源回退、实际字节复验和取消规则；任一页或清单遍历失败，整次调用不返回完成报告，必须等待所有在途工作退出。外层仍核对封口清单总数/字节数及新鲜 Root/来源注册，普通后续轮次可凭真实已有字节续跑，不缓存持有证明或生成额外任务状态。

普通 live repair 的有界页也复用上述小记录批次，不增加传输槽或引入新的后台调度。正式 worker 每页最多 64 条元数据；先通过 Owner ReadIndex 验证引用，再按“缺少索引”与“有效索引但旧 Pack 不可读”分别形成最多 32 条 / 4 MiB 的批次。后一类通过 `RepairExisting` 搬入健康卷；缺少、损坏或已关闭的索引不能借搬迁路径创建或覆盖。每条仍执行原来的实际持有检查，页末仍复查 Root cohort；批次预填充本身不算持有或多数确认。

批次来源不齐或可重试失败时保留原逐条修复路径，权限和协议错误直接失败；旧端点只允许在任何帧返回前的 Unimplemented 回退。目标无可写卷或空间不足时交回原容量协调路径，已明确卸载到其他节点的记录不通过本地批次重复写回。单次传输可能留下已验证的部分本地写入，但后续必须逐条验读，不能凭批次返回值清除欠账。上述页和载荷上限不等于全进程 RSS 上限。

新成员候选发布前的完整封口清单多数复验，每 64 次远端物理持有观察获得一个新的 Root 确认切点；观察 RPC 复用现有已确认切点协议，接收端仍要求本地 Root 已应用该位置、验证调用者/自身当前成员身份，并逐条实际读验 Pack。所有描述、独立 Node/Store 和严格多数检查不变，最终仍须重新确认完整清单统计、候选成员注册和 Root 待定交接计划；不跨轮保存持有证明，不把历史页算作新一轮多数。两分钟协调轮次上限保持不变。

区域栅栏观察 RPC 独立限制为最多 8 个活动处理槽、4 KiB 请求、各 1 MiB 的栅栏和交接记录、256 KiB ConfState，总响应不超过 2 MiB + 256 KiB + 4 KiB；客户端与服务端都有 10 秒内部上下文，过载立即拒绝。检查指定参与者的 Root/Group 读屏障，成员/栅栏/交接来自同一切点，不跟随 leader 重定向，不累积后台等待 goroutine。槽在 protobuf 解码后计数，不覆盖连接/握手或全部解码开销；上下文不能强制中断磁盘。见[区域栅栏与远端观察](../architecture/region-fences.md)。

初始区域集合确认、建组与严格增长共用每节点串行后台任务；初始确认和增长各自每轮仅选一个区域，逐参与者观察，最多 20 秒且受整轮 30 秒上下文约束。增长探测每个候选节点最多 3 秒，起点轮转；封口/候选全员检查不因探测选择而缩小。轮转调度不按健康缩小参与集合，也不跨轮缓存过期证据；关闭需等待任务退出。4096 个成员的格式上限不是完成时间或已验证生产规模承诺；大规模/WAN 调度与 IO 公平性仍待实测和完善。

数据成员 Change、PrepareJoining、TransferLeadership RPC 共用最多 8 个活动请求、10 秒内部上下文；过载立即拒绝，取消后释放处理槽。ConfState 不超过 256 KiB，Change/Transfer 请求和 Inspect/Change 响应不超过 256 KiB + 4 KiB，准备请求与准备/转移响应不超过 4 KiB，客户端也设置对应消息上限。Inspect 尚未共用并发准入，且磁盘/已有临界区无法被强制中断，不能将这些限制当作所有成员服务的总内存或硬性执行时间上限。详见[成员任务与位置栅栏](../architecture/group-membership.md)。

Node 续期 RPC 独立限制为最多 4 个处理槽、32 KiB 协议消息和 30 秒上下文；不接受 CSR/可选公钥。槽在 protobuf 解码后计数，不是全局连接/解码预算。客户端每次最多三次 5 秒 RPC 尝试，仅重试临时不可用/超时；后台外层每轮 1 分钟上下文，失败抖动退避，不能强制中断磁盘 Sync。正式 Server 关闭须等待续期工作者结束才释放 Store。详细策略见[节点加入与续期](../architecture/node-enrollment.md)。

`internal/platform/resource` 测试预算耗尽、整数边界、并发预约及重复释放；`raftrpc/resource_test.go` 覆盖跨 Peer 共享、活动请求占用、控制通道绕过阻塞日志、队列拒绝、关闭回收、接收并发/字节拒绝、取消/坏帧回收，以及预约持有到持久安装结束。实际 mTLS 集群复制/快照追赶仍由原有集成测试覆盖。

本地当前引用修复使用一个固定工作者，与 Geo 修复共享同一维护 IO 令牌桶，但不再等待 Geo/备份/迁移的独占作业槽；否则连续 WAN Geo 页可使区域 leader 的确认扫描长时间得不到运行机会。本地页仍最多 64 条，载荷逐条处理，传输仍使用原共享活动请求、字节预算及两分钟页期限。Geo、备份、迁移之间的独占关系不变。该调整允许本地修复与一个独占作业并行，保持原有 IO 限速与传输准入；不宣称全进程 RSS 上限或新增的数据耐久证明。

Geo 确认的代际刷新对小记录每页最多处理 32 条，不扩大物理修复批次。页内共用批首 Root 确认，批末重新确认 Root、各 Range 映射和 Region 计划；每条仍独立验证实际物理多数、持久镜像和 Owner 确认。健康记录可直接完成此确认，避免先做一轮独立物理修复检查；失败记录继续进入原物理修复路径。匹配的历史回执不代替新的物理观察。状态中的 Geo 待办数量仅反映持久提示队列，不是全库尚未刷新的代际回执总数。

全局 Geo 旧回执发现由当前 Owner Group Leader 调度；失去 Leader 身份时丢弃该进程的发现游标，后继 Leader 从首批重新扫描。每台节点仍独立重试已有持久物理欠账和镜像欠账。确认页合计载荷不超过 4 MiB 时，最多 32 条共享页首与页末 Root 检查，物理观察仍最多八条并行。候选页超过该载荷门限时，worker 回退到原来的八条页；八条页仍超过门限则顺序验证，保留大记录原有资源行为。页取消必须等待所有工作退出，服务端持有检查槽和传输预算保持原值。镜像重试队列为空时不查询 Root；非空任务仍取得新鲜 Root 授权，查询失败保留持久待办。这些局部界限不是整个进程的 RSS 硬上限。

支持批量镜像的小记录页先共用一个新鲜 Owner 切点核对各引用，再完成物理多数准备；此切点仅供准备阶段使用，绝不能确认之后提交的命令。准备后不保留载荷，最多 32 条元数据事项一起进入确认池。池按目标节点和 Group 合并当前已就绪的事项，不等待凑满；每次镜像 RPC 最多 32 条、编码命令合计最多 256 KiB，协议封装另限 4 KiB，每批最多 3 秒。服务端最多两个批量镜像处理槽，每条仍提交原确定性命令，然后共用一次新鲜 quorum cut，并逐条匹配精确持久 Result；仅入队或结果未落地返回该条待重试，不拖住已完成项。大于批量字节界限但原单条协议允许的命令仍走单条路径。

确认池将可重试项排到已等待事项后面，和下一批就绪事项重新组批；对同一选定目标最多尝试三次，或调用方期限先到后，交回原候选/修复逻辑。权限拒绝、损坏响应、命令冲突和持久拒绝不在池内盲重试。成功镜像按精确持久结果从待办中清除，后台确认页可合批清除，其他失败不使成功项重新入队；失败及重试耗尽始终保留为待修复欠账，不能宣布安全或缩小多数派。重启后持久轮转游标仍让尚未尝试的项先推进。

Geo 镜像待办在发送之前同步持久化：每个 Pebble 写批最多 32 条，编码后的 Key/Value 总量最多 4 MiB，单条仍最多 1 MiB。已完成物理准备的小记录页先合并保存待办，再启动确认工作者；各记录发送前仍检查/保存自己的待办，防止并发修复刚好清除了该项。完全相同且已持久保存的内容不重复写 WAL；同一个确定性 Key 下内容不一致则报错。多批保存不是跨批事务，后续批失败可能留下已保存的前缀作为修复欠账，绝不算确认成功。失败项和轮转顺序不变。

待办保存、删除和轮转游标写入遇到 WAL 同步错误（包括 Pebble 的已知存储 FatalError）后，将当前账本句柄标为失败，后续读写均返回失败；重新打开时从恢复后的持久键重建计数，不用内存计数推断同步失败时的结果。无关的程序 panic 不被吞掉。`repair.mirror_save` 现在计量一次批量保存调用（包括页级预存和每条记录发送前的幂等保存），其调用次数不能与旧版逐条 Save 数直接等同比较。


Geo 元数据提交阶段同时等待 Owner 确认的事项也可合并 ReadIndex：只有开始取得切点之前已经进入该批的请求可共用结果，执行中和完成后到达的请求必须使用下一次新鲜切点。每条继续检查自己的引用、实时 Range fence、命令哈希和持久结果；最终 Root/Range/Region 复核失败时整页不返回可清账结果。所有池仅存在于一个有界页/重试轮内，取消须等待在途工作退出。元数据等待者增加到最多 32 个不扩大实际 Pack IO 并发或载荷门槛；这不是全进程 RSS 预算。

支持本地批量提交的后台 Geo 确认页，还会合并当前已就绪、同一 Owner Group 的提案：最多 32 条、原始命令合计 256 KiB，不等待凑满，不重试提交，也不把多条命令变成事务。Group 对每条分别执行命令校验和磁盘准入，再共用一次 Ready 处理；每条仍是独立 Raft 日志与状态机应用。单条校验/准入失败只返回该条错误，共享运行时或存储失败则整批返回错误，不能猜测哪些项已经提交。接受提案不代表持久成功，调用方仍通过新鲜 ReadIndex 和精确命令结果确认。大命令、其他 Group 以及没有批量提交能力的调用方沿用单条路径；普通前台写入和 Root 提交没有接入此收集器。

提案收集器仅存在于当前页，取消时必须等待正在执行的批次退出；上下文不能强行中断已有同步磁盘操作。`repair.owner_submit` 保持逐命令计时并包含收集器排队和批次完成等待，不用批次数减少掩盖单条等待。

小记录后台 Geo 确认页将已取得精确成功持久结果的镜像收集在当前页内，容量不超过该页准备的镜像总数。所有页工作者退出后（包括取消）同步清账，每个 Pebble 删除批最多 32 个确定性键、键总量最多 4 KiB；没有计时器、新的后台工作者或持久队列。只删除成功镜像的精确键，不删除另一代 Region 或另一条发布记录的待办；重复/已不存在的键不重复减计数。取消时未确认结果的项留待重试，已取得成功结果的项仍可清除。页末清账失败不返回成功页结果，句柄按原同步失败规则停止使用，重开后重建计数。进程在清账前中断只会遗留可幂等重试的成功项，不会提前删除未完成项。多个删除批不是跨批事务，前批可成功而后批失败。

普通单条确认、前台镜像和独立持久重试轮仍在逐项成功后清账。后台页的 `repair.mirror_delete` 现在按页计量同步批量清账，旧版是各工作者逐项删除及排队时间，调用粒度不同；比较优化必须同时看页耗时、整轮耗时及最终欠账，不能把调用次数或并行累计等待的减少直接当成墙钟提速。

上述小记录确认页将同一目标节点的持有观察合成一个 `ObserveBatch` 请求，最多 32 条、声明载荷合计不超过 4 MiB；只传描述和持有结果，RPC 消息上限为 `32 * recordHoldingMessageBytes + 4096`。接收端与单条接口共用原两个处理槽、八个排队槽和超时，逐条读取并校验实际 Pack 字节，返回前再次验证调用者和本机的 Root 成员身份。每行必须是匹配请求顺序的完整持有证明或有界存储错误；客户端整批校验 TLS 对端、身份、Root 切点和全部行，身份或协议错误不暴露部分成功结果。页内最多缓存八个目标的元数据，超过后走原单条路径；缓存随本页结束释放，不跨页使用。旧节点只有明确返回 Unimplemented 时才回退单条接口，拒绝、超时或坏响应不得借回退绕过。Owner 的逐条引用、物理多数、持久镜像/回执以及批末新鲜 Root/Range/Region 复核保持不变。

后台分段诊断复用现有 `DUBI_TRACE_DATA=1` 开关，默认关闭。local/geo 每轮各生成至多一条 `dubi_repair_timing` 聚合日志；只接收 13 个固定阶段名，计数、累计微秒与单次最大值保留在固定数组中，未知标签丢弃。并发与嵌套阶段会重叠，累计耗时不能直接相加当作墙钟时间；失败调用也计入等待，日志不是耐久性证明。关闭聚合后忽略迟到回调，不扩大请求槽、载荷预算或取消期限；Observer 包装保留批量持有接口。日志不含租户 Key、载荷、RequestID 或动态 Peer 标签，诊断窗口结束后应恢复默认开关。

Geo 代际确认在其精确 Owner 发布和物理 Region 多数已验证后，针对本机拥有的 Owner Group 优先使用本地提交与持久结果等待，避免经另一成员转发同一区域的镜像。偏好只从当前计划的成员副本中选择，不增减成员或修改计划；命令仍为原确定性 MirrorGeo，必须经 Owner quorum cut 读取匹配哈希的持久 Result，不能用 Submit 成功当作完成。其他 Region 使用上述认证批量 RPC，单条和大记录保留原路径；本地镜像不是物理 Pack 持有证明。

本地确认代际刷新仍每页最多 64 条，但独立记录不再逐条等待 Raft 结果；它与 Geo 确认共用至多八个工作者及 4 MiB 合计载荷门槛，大页继续串行处理。逐条实际物理多数、精确引用、Owner 持久结果以及页首/页末 Root 计划复核不变，错误仍按原引用顺序返回；取消也须等待所有工作者退出。这只调整后台确认等待的并行度，不更改前台写入 ACK 或读授权，也不将当前队列长度当成整个库的收敛剩余量。

本地修复 worker 将“检查待刷新回执”和“刷新过期回执”合并到同一个最多 64 条的确认调用。两步共用本次刚取得的 Root 切点，结束时再取得新鲜 Root 确认并核对 Region 计划；不将切点缓存给后续页或前台请求。已有当前回执的一整页仍只用一次 Owner 屏障过滤，不逐条重复读取或提交；需要刷新时仍逐条验证当前引用、实际物理多数、持久结果和实时 Range fence。最终 Root/计划失败不给调用方完成结果，原修复游标和欠账不能据此前进。八个工作者及 4 MiB 门限不变。

读取遇到已证明当前物理多数、但区域确认过期的小记录时，每个节点允许最多一个同步确认刷新，不设等待队列。上限为 4 MiB，刷新上下文最多 5 秒且服从调用方期限；仅当前 Owner leader 执行。刷新后完整重读一次，不能递归重试；超限或繁忙走原有回退/后台修复。此期限约束可取消的屏障和 RPC，不承诺能中断已经进入的同步磁盘提交。

本地确认修复页复用有界 Owner 读屏障与提案收集器：只有屏障开始前已入批的等待者共享此次新鲜切点，后来者进入下一批；提案最多 32 条 / 256 KiB，不为凑批增加定时等待。物理工作仍最多 8 个并发，大载荷继续串行，每条精确持久 Result、物理多数和最终计划检查不省略。

本地修复的物理阶段和本地确认阶段可共享同一页的 Root 准入切点，整个页受原有两分钟期限限制；结束前必须重新取得 Root 多数切点并比较区域计划，再推进持久游标。Owner 切点不被这个 Root 缓存复用，前台读写不使用该缓存，下一页重新准入。

本页处理完正常记录后，仅因所有候选来源临时 Unavailable/DeadlineExceeded 而失败的行可在页尾额外尝试一次：最多 8 条，合计载荷不超过 4 MiB，共用最多 3 秒的上下文。重试前重新确认精确 Owner 引用，实际本地 Pack 校验成功才消除该行失败；权限/身份错误、缺失、损坏、不可用本地 Store 或仅其他节点修复成功不适用。超限、超时、覆盖或仍失败的行照旧计入持久欠账；已有历史欠账不被本页重试清除。无新增持久格式、后台任务或运维参数。此优化只减少能够在短窗口内恢复的瞬时失败造成的额外全扫，不能替代持续故障后的完整干净扫描。

Geo 发现阶段刚取得的 Root 多数切点，可作为同一次后台尝试紧接着的第一张确认页的准入切点，避免发现后立即重复 ReadIndex。只消费一次，即使该页失败也不交给后续页；后续页和物理修复后的确认重试仍自行取得新切点。不保存到 worker 字段、持久游标或下一轮，整个尝试仍受原两分钟期限约束。确认页必须检查本机 Root 已应用该切点，逐条验证物理多数和精确持久结果，末尾再次取得新鲜 Root 多数切点并比较各 Range 映射与 Region 计划，失败不返回可清账结果。前台请求和远端成员认证不使用这个发现切点优化，页大小、IO 并发、载荷上限均不变。

新节点补齐后、发布下一代区域之前的全量候选校验，也使用已有批量持有 RPC。每页最多 32 条描述、声明载荷合计 4 MiB；页内按需要向目标节点获取观察，最多保留八个目标的结果，额外目标和超过 4 MiB 的单条走原逐条路径。只保留描述和证明元数据，不缓存载荷，不增加 IO 并发或后台任务；下一页丢弃观察结果。Root 切点预算按实际请求的物理观察行数计算，每次最多 64 行，不能因一次 RPC 带多行而扩大预算。旧节点明确返回 Unimplemented 才回退逐条请求，权限和坏响应不会借回退绕过验证。

候选校验继续逐条验证本地实际 Pack、远端身份、描述和不同 Store 的物理多数，完整清单摘要、引用数量和总字节也必须一致。任一条不足多数、取消或清单验证失败都不返回部分完成报告；最终待定区域计划与成员身份复核和 Root 发布条件保持不变。现有 `DUBI_TRACE_DATA=1` 下，candidate-fill / candidate-verify 各记录总耗时与工作耗时，包含失败尝试；总耗时覆盖准入、授权和工作，工作耗时包含封存清单获取及复核，二者不能相加。日志不记录租户 Key、封存内容或请求身份，默认关闭。
